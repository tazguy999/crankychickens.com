Engineering Methodology

Controlled AI Development

A portable framework for engineering teams building with AI-assisted development.

Nick Weber  ·  v1.0  ·  2026  ·  See it in operation →

1. The Problem

AI coding tools compress the easy 80% of any feature dramatically. A scaffold, a component, a CRUD endpoint — done in minutes instead of hours. Stakeholders see this happen and permanently recalibrate their expectations. Every future estimate gets divided by 10 in their head.

Then you hit the hard 20%. Race conditions. Edge cases. Domain-specific constraints that AI doesn't have access to. The gap isn't a conversation anymore — it's a credibility crisis. AI didn't compress the hard part. It just made the contrast more violent.

The 80/20 Trap: AI unlocks the easy part first. Always. The danger isn't slow delivery — it's that speed on the easy 80% creates expectations that the hard 20% can never meet.

A second problem compounds this: AI tools generate plausible-looking output that optimizes for immediate functionality over coherent architecture. Code that works today but accumulates what we call vibe debt — a growing gap between what the codebase appears to be and what it actually is. Vibe debt is invisible until it becomes a crisis.

The root cause of both problems is the same: development driven by vibes instead of specifications. A developer changes a prompt, tests a few inputs, and if it looks good to them (LGTM), they ship. This is guesswork dressed up as engineering.

2. The Framework

Controlled AI Development treats AI-assisted engineering the way lean manufacturing treats a production line: instrument the process, establish a baseline, introduce controlled changes, measure outcomes objectively. Not vibes. Not LGTM. Not guesswork.

2.1 · Acceptance Criteria as Specification

No code is written until testable acceptance criteria exist and are approved. A ticket description is intent. Acceptance criteria are verification conditions. The distinction matters because AI will make decisions about every ambiguity silently.

  • Testable: each item is either pass or fail, not a matter of judgment
  • Explicit about scope: what is out of scope is as important as what is in scope
  • Approved before development starts: AC written after the fact is not AC, it's documentation
Gate
Ticket status is not Ready until AC exists and is approved. AC lives on the ticket as a versioned comment, not in a chat message.

2.2 · Prompts as Source Artifacts

If the prompt is the specification that drives AI output, the prompt is source code. It deserves the same treatment: version control, review, and ownership. Reviewing only the generated output without reviewing the prompt is like reviewing a compiled binary without access to the source.

  • Prompts are tracked: session telemetry captures what was sent, not just what was received
  • Patterns are reviewable: engineering lead can see prompt sequences, not just PR diffs
  • Changes are deliberate: prompt modifications are treated as interventions with measurable outcomes

The most important review a lead can do is not the code review. It is the prompt review — the review of the specification that generated the code.

2.3 · Sessions as Observable Pipelines

An AI coding session is a black box unless instrumented. Claude Code exposes native OpenTelemetry support that, with a single environment variable, streams session data to any observability backend.

What telemetry captures per session: every prompt and its character count, token usage, tool calls made, cache hit ratio (a proxy for prompt structure quality), model and estimated cost.

The key diagnostic signal is the beast mode flag — a single massive prompt that attempts diagnosis and resolution simultaneously, with no checkpoint between them. AI confidently resolves the wrong thing because it diagnosed wrong inside a single context window. Telemetry makes this pattern visible without watching the developer work.

Setup
CLAUDE_CODE_ENABLE_TELEMETRY=1
OTEL_LOG_USER_PROMPTS=1
// one-time shell profile config, zero ongoing friction

2.4 · Goldilocks Fixtures as the Regression Gate

A Goldilocks fixture set is a curated collection of input/output pairs that define ground truth. Not too broad, not too narrow — just right for the specific thing being tested. Derived directly from approved acceptance criteria. Gates the PR.

  • Objective fixtures: deterministic assertions. Run on every commit. Fast and cheap.
  • Rubric fixtures: binary pass/fail on subjective outputs, scored against explicit criteria. Run on PR.

The critical distinction from traditional tests: Goldilocks fixtures test the pipeline (ticket → prompts → output), not just the code. A prompt change that regresses fixture performance is caught before it reaches review.

Gate
PR cannot merge if Goldilocks assertions fail. Fixture failures communicate "this isn't done yet" in objective terms — no conversation required.

3. The Fellowship Model

The TDD discipline that governs how tests are written within this framework. It exists because AI agents, left to their own devices, will delete tests to make them pass. The Fellowship Model makes the test the specification, not an afterthought.

Gather the Party
Arrange — define all inputs and dependencies, create mocks and stubs as needed
Do Adventure
Act (Black Box) — call the public method only. Do not implement internals. The test must fail initially.
Claim the Treasure
Assert — verify expected output and interactions with dependencies

If we defeat the dragon on the first move, we skipped the story. The red phase is not a formality. It is proof that the test is testing something real.

4. Portability

This framework was developed in the context of a B2B SaaS engineering team. The specific tooling — ADO for tickets, App Insights for telemetry, Claude Code for AI assistance — is not what travels. The discipline travels.

What travels to any team, any domain

  • The AC gate: ticket isn't ready without testable acceptance criteria. No tooling required.
  • The Goldilocks habit: fixtures change with the domain, but the discipline of maintaining ground truth is universal.
  • The eval loop: baseline → intervention → measure is scientific method. Works on any prompt, any model.
  • The beast mode flag: a human judgment call about prompt structure. Domain-agnostic.
  • The Fellowship Model: TDD discipline that pre-dates AI and becomes more important as AI generates more code.

What stays with the originating team

  • The specific Goldilocks fixture sets — they encode domain knowledge
  • The slash commands and ops automation — wired to specific ADO and Notion structures
  • The two-lane product strategy — the moat analysis is domain-specific

What an engineering leader brings to a new context is not tooling. It is this document — the reasoning behind each gate, the failure mode each component addresses, and the implementation pattern that works at small team scale. The new team builds their own fixtures. The skeleton is reusable.

5. The Standard We Hold

Done means transferable.
Any teammate should be able to understand, debug, and extend the work without the author in the room.
QA catches what you didn't anticipate.
You own what you could have.
Prompts are source.
If you can't show the prompt, you can't explain the output.
Measurement over vibes.
An improvement that can't be measured isn't an improvement — it's a preference.

This is an aspirational standard. The methodology itself is under continuous improvement using the same eval loop it prescribes. The goal is not perfection. The goal is a repeatable process for getting demonstrably better.
