Engineering Philosophy

TDD Tests
as Specs

The spec is the business rule as devs understand it. Tests make that understanding executable — and reversible.

The Core Idea

Tests written before the code aren't tests — they're specifications. If you can't write the test first, you don't understand the requirement well enough to build it. The failing test is the only honest measure of "done."

What This Unlocks

Acceptance criteria get defined before anyone touches implementation. Refactoring becomes fearless — the spec didn't change, only the internals. New team members (or AI agents) can understand intent from the tests alone, without relying on comments or docs that rot over time.

Where Teams Get It Wrong

Writing tests after the fact as a coverage checkbox produces implementation transcripts, not specs. They test what the code does, not what it should do. When the code is wrong, so is the test.

The Signal Test

❌ Mirror — not a spec
testSaveUser()
✓ Behavior — this is a spec
should_reject_duplicate_
email_on_registration()

If your test name reads like a method, it's mirroring the implementation. Spec names describe outcomes a user or stakeholder would recognize.

The Bidirectional Loop
Dev → AI
Spec In

The test communicates intent without ambiguity. Natural language requirements are lossy — a well-named test with clear assertions is precise. The AI builds to the contract, not to its interpretation of a prose ticket.

⇄
AI → Human
Plain English Out

Run it in reverse: the AI reads the test suite and produces stakeholder-readable business rules. No more "what does this actually do" conversations — the tests are the answer, just translated.

What This Closes

The classic gap is requirements → code → reality, where each handoff introduces drift. Specs-as-tests make requirements executable, so drift is immediately visible as a failing test — not a production bug six weeks later.

The Audit Built In

When an AI summarizes a test as "system allows duplicate emails on registration" and that sounds wrong to a stakeholder — you caught a spec error before it ever ran. The reverse translation isn't just documentation. It's a free correctness check on your own understanding of the business rule.

The real value: Tests aren't just about code correctness. They're a shared language between devs, AI agents, and stakeholders. Written in one direction, they drive implementation. Read in the other, they produce living documentation. The same artifact does both.

🐔 explained for game devs
🐔 Cranky Chickens Edition

Writing a Spec for the Cannon

Let's walk through a real feature from Cranky Chickens: In Space — the cannon shot — and turn it into a proper spec. Same rules the pros use.

1
Start with the rule in plain English

Before writing any code, write down what the feature should do in a sentence a non-coder could understand. This is the business rule.

🐉 Dragon Scribe writes the rule
"When the cannon fires, the cannonball should travel forward and disappear when it hits a wall or leaves the screen."
2
Turn the rule into a spec (the test name)

The test name IS the spec. Say it out loud — if it sounds like something that should happen in the game, you've got it right.

❌ Not a spec
testCannonball()
Tells us nothing. What should happen?
✓ This is a spec
cannonball_disappears_
on_wall_collision()
Anyone reading this knows exactly what rule it's checking.
3
Hand it to the AI builder

The spec is the contract. You give the AI the test — it writes the code that makes it pass. It doesn't get to decide what "disappear" means. You already decided that in step 1.

🐉 Dragon Scribe
writes the spec
→
🤖 AI Builder
makes it pass
→
✓ Test passes
feature is done
4
Run it backwards — AI explains the test

Now flip it. Ask the AI to read the test and explain it in plain English. If its explanation matches your rule from step 1 — the spec is correct. If it doesn't — the spec has a bug, not the code.

🤖 AI reads the test, says back:
"When a cannonball hits a wall, it is removed from the game world and no longer renders on screen."

That matches what Dragon Scribe wrote. ✓ Ship it.

The spec is how you tell the AI what you mean. The reverse translation is how you check the AI understood. Same test. Both directions. That's the whole trick.

🐔 What Comes Next

How the Flock
Gets Bigger

Writing one spec for the cannon is the beginning. Here's how the whole mission control grows from here — one chicken at a time.

Where most devs start
🤖 AI as the Helper Chicken

You're building the whole game yourself. The AI just sits next to you and whispers suggestions — "maybe the cannonball should go faster?" You can take the idea or ignore it. You're still doing all the real work.

AI suggests, you decide everything
Where specs put you
🐉 Dragon Scribe gives the orders

Now you write the rule — "cannonball disappears on wall collision" — and the AI builds it. You stopped being the one who does all the building. You became the one who decides what the game should do. That's a bigger job.

🗺️ You are here
The next level
🐔🐔🐔 A whole flock of AI builders

One spec fans out to a whole crew. One AI builds the cannon. Another tests it. Another checks the work. Dragon Scribe writes the rules — the flock executes them in parallel. The game gets built way faster, and Dragon Scribe is running Mission Control.

🚀 Happening right now
The final boss level
🥚 AI that writes its own specs

The AI watches players get stuck on the wall collision bug, figures out the rule is missing, and drafts a new spec for Dragon Scribe to review. Dragon Scribe just says yes or no. The job becomes: decide what's true about the game. Everything else is automated.

🌌 On the horizon
🐔 The point

At every level, the spec is the most important thing. Code gets generated. Tests run themselves. Bugs get caught automatically. But someone has to decide what the game should actually do — and that's always a person. The devs who get good at writing clear rules are the ones who stay in charge of the flock, no matter how big it gets.
