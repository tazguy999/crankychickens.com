Post-Ship Methodology

Cold Read

AI looks at the work artifact trail with no prior estimate in hand and tells you what the work was actually worth. No anchoring bias. No human memory. Just the evidence.

Nick Weber  ·  v1.0  ·  2026  ·  Read Measurement Layer first →

1. What It Is

After an epic ships, feed the complete artifact trail — commits, PRs, repos touched, ADO work items, meeting journals, blockers encountered — to AI with no estimate attached. Ask what it would have called the work. Cold. No anchoring bias from the original estimate. No human memory of how it felt to be in it.

"AI, you have full context. You have no anchoring bias from the original estimate. What would you have said this was worth?"

The output isn't a verdict on whether you estimated correctly. It's an unanchored structural assessment of what the work actually was — derived from what it left behind, not from what anyone remembers about it.

The delta between the cold read and your actual tier is tier drift. Over time, tier drift is the most honest signal your planning system produces.

2. Why It's Not a Retro

The overlap is that both happen post-ship. That's it.

Retrospective
Asks: how did we do and what do we change
Facing: team-facing, process-focused
Input: human reflection
Contaminated by: mood, politics, recency bias, who was in the room
Output: lessons, action items
Cold Read
Asks: what was this work actually worth
Facing: system-facing, complexity-focused
Input: artifact trail
Contaminated by: nothing — AI never saw the estimate
Output: complexity class, classification rules

A retro would have surfaced "Azure B2C was hard." The cold read surfaced why it was hard in structural terms — undocumented third-party behavior only discoverable in a live environment. That's not a feeling. That's a classification rule for future work.

The retro tells you what happened. The cold read tells you what the work was. Those are different things.

3. The Artifact Trail

The cold read is only as good as what you feed it. These are the inputs, in rough order of signal value.

Commits + PRs
Highest signal. Objective. Repos touched, diff size, number of files changed, review cycles. This is where complexity lived.
ADO Work Items
Ticket descriptions, AC, linked bugs, blocked states. Shows what was scoped and what grew during the work.
Repo Count
Strong multiplier signal. 4+ repos in a single feature means integration surprises compound. Every boundary is a place something unexpected lives.
Blockers Hit
Especially: undocumented third-party behavior, environment-only bugs, external API surprises. These are only discoverable in a live environment. You can't read your way out of them.
Meeting Journals
Wayfind/team journal context. Interpretive — already filtered by whoever was in the room. Useful, not objective. Weight accordingly.
Domain Survey
What did the pre-build context scan surface? Mismatches between the domain survey output and what was actually found are their own signal.
Engineer Tenure
How familiar were the engineers with the codebase? New engineers in an unfamiliar domain is a complexity multiplier the ticket doesn't capture.

The honest caveat: the cold read has no anchoring bias on the estimate, but it inherits whatever bias exists in the input artifacts. Commits are objective. Meeting notes are not. Name this explicitly in your read.

The output isn't blame. The output is a classification rule your tier system can now encode. Next time work has this profile, you have a data point. Knowing the shape of a class of work upfront changes how you sequence it — not how long it takes.

5. Tier Drift

Cold read tier minus entry tier. Run it on every epic. After six months you'll see patterns that no retro would ever surface.

Drift
What it means
Action
+2 or more
Systematic underestimation. The work consistently costs more than its class suggests.
Encode a complexity multiplier for this profile.
+1
Normal. One tier of unknown unknowns is expected in most delivery.
Watch for patterns. Single data point doesn't move the system.
0
Accurate classification. Your tier system is working for this work type.
No action. This is the signal you're calibrating toward.
−1 or less
Overestimated. Could mean the team is getting faster, or the tier ceiling is too conservative.
Check if domain familiarity or tooling explains the delta.

Over enough cold reads, tier drift across your whole ticket history tells you:

  • Where your classification system is systematically wrong
  • Which domains you consistently underestimate
  • Whether certain engineers or work types drift more than others
  • When your green tier is hiding yellow work

This is also what answers the "why not just ship when done" question with data over time. You're not guessing at complexity. You're building an evidence base that shows what work actually costs — and where your planning system needs to be smarter.

6. The /cold-read Command

Feed it a ticket ID. It pulls the full artifact trail and returns the structural assessment. No estimate required — that's the whole point.

// Usage
/cold-read <ticket-id>

// Example
/cold-read US-7347

// With range
/cold-read US-7347 US-7387 // treats as single epic

What it pulls

Commits and PRs across all repos linked to the ticket. ADO work item history including blocked states and scope changes. Wayfind journal entries tagged to the work. Domain survey output if one was run. Engineer assignment and tenure in the codebase.

What it does not need

The original estimate. Story points. Any human input about how the work felt. The cold read is cold because it never saw those. That's the mechanism, not a limitation.

Codebook

The cold read output must include: complexity class (time range), cold read tier, tier drift, and at least one named structural finding. A structural finding is a classification rule — a generalizable claim about what work with this profile costs, not a comment about this specific ticket.

"Azure B2C was hard" is not a structural finding. "Work touching undocumented third-party auth behavior is only discoverable in a live environment and cannot be scoped from documentation alone" is a structural finding. Encode it. Use it next time.

7. When to Run It

Every epic at close. Not every ticket — epics. The artifact trail needs enough density to be meaningful. A single-ticket PR has too thin a trail. An epic that ran two weeks or more has enough.

First three months

Don't do anything with the data. Just collect it. Run the read, log the output, move on. The patterns aren't visible in individual cold reads — they're visible in the aggregate. You need a minimum of eight to ten reads before the tier drift starts meaning anything.

Month four onward

Start encoding. Every structural finding that appears in three or more reads becomes a classification rule. Add it to the tier system. Raise the floor for that work profile. Stop being surprised by the same class of work twice.

The cost of running this consistently is near zero. Five minutes to pull the artifacts. Ten minutes for the read. The output you get is already better signal than any sprint retro. The only reason not to do it is forgetting to.
